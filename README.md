## v9.26 実機不具合修正版（2026-11-07）

v9.25 の実機初回セッションで確認された不具合2件と、起動時ログの小掃除を行いました。

**修正1: ウォッチドッグ・リセット（TG1WDT_SYS_RESET／reset reason INT_WDT）**

実機ログの経過：起動直後のダンス自動再生はヒープ不足（free 51,752）でガードが正しく見送り。その後のニュース取得（Google RSS、開始時 free 51,432／largest 49,140）で既読・旧記事のスキップが続いた後、`[Google RSS] headlines:` の完了行が出ないままリセットしました。再起動後は free heap 197,344 まで回復し、再発はログ範囲内では無し。

根本原因の最有力候補は、**既読ストアの SPIFFS 保存が RSS ストリーム走査の最中に走っていた**ことです。従来、`newsAcceptArticle()` が記事を採用するたびに `newsSeenAdd()` → `newsSeenSave()` が SPIFFS へ全件書き戻しをしていました。ESP32 のフラッシュ書き込み・消去は、実行中は他コアをキャッシュ無効化で割り込み禁止のまま止めるため、消去が長引く（セクタ消去のワーストケースや SPIFFS の GC 連鎖）と割り込みウォッチドッグ（TG1、300ms）を踏み得ます。完了行が出ず、panic 出力もないハードリセットである点と整合します（単一ログからの断定はできないため、下記のとおり「止まらない構造」への変更と、再発時に箇所を特定できる仕組みを併せて入れました）。

- **保存の後段一括化**：`newsSeenAdd()` はメモリ上の記録とダーティーフラグだけ更新し、SPIFFS への書き戻しは取得完了後（TLS を閉じた後）に `newsSeenFlush()` が1回だけ行います（`exec_news`／`exec_news_category`／Function Calling の `get_news` の各出口。加えて loop のアイドル時にダーティーが残っていれば保存する保険付き）。書き込み回数は1回の読み上げあたり最大5回程度→1回に減ります。
- **取得ループの分割と yield**：Google 見出し走査は約1KB ごと、NHK 本文読みは約4KB ごとに `delay(1)` を挟み、データが流れ続ける場合でも loop を独占しないようにしました（従来はデータがある間 delay なしで回り続けていました）。
- **低ヒープ時の安全弁**：`exec_news` の2本目（AIニュース）の TLS ハンドシェイクは、free heap 45,000 以上かつ最大連続ブロック 40,000 以上のときだけ行い、不足時は `[News] AI feed skipped: low heap` を出して一般ニュースだけで読み上げます（閾値は実測の動作点 largest=49,140 に余裕を持たせた値）。
- **起動時ダンス自動再生の見直し**：発火条件を「起動3秒後・Wi-Fi接続」から「穏やかな瞬間」に変更しました。起動10秒以降、ヒープ 80KB 以上（自動再生専用の下限。再生自体のガード 60KB は不変）、発話・合成なし、TLS ゲート空き、メニュー／ダイアログなし、が揃うまで最大120秒待ち、揃わなければ自動再生だけ見送ります（音声トリガーの再生は従来どおり）。先送り・見送りは `[DANCE] boot autoplay deferred/skipped` で理由つきで出ます。
- **パンくずログ**：loop の主要区間の入口で現在区間名を記録し（`news-nhk`／`news-google`／`news`／`news-cat`／`chat`／`chat-tools`／`stt`／`dance`／`mem-extract`／`spiffs-seen`／`loop`）、loop が15秒ごとに `[HB] t=<ms> heap=<free> largest=<最大連続> crumb=<区間> mode=<m> seen_dirty=<0/1>` を出力します。再発時はリセット直前の `[HB]` の `crumb` が最後にいた区間、`heap`／`largest` が逼迫度を示します。

## v9.25 Function Calling＋長期記憶メモリ版（2026-11-07）

会話 AI（ChatGPT）に Function Calling のツールを持たせ、声で実作業ができるようにしました。あわせて、会話から「覚えるべきこと」を抽出して本体に保存する長期記憶メモリを追加しました。**版数について**：このブランチでは v9.24 を「通常動作とBLE転送のモード分離（開発版）」が使用済みのため、本機能は **v9.25** としました。v9.25 は v9.24（モード分離）を含む、v9.23 の次の配布版です。

**Function Calling**: 会話経路（音声 `exec_chatGPT` と HTTP `/chat` の共通位置）に tools を追加し、tool_calls の実行→結果返却→再リクエストのループ（往復最大3回）を実装しました。使えるツールは次の6つです。

| ツール | 内容 |
| --- | --- |
| `set_timer` | 単発タイマー。`minutes`（何分後・相対）と `time`（HH:MM・絶対）の排他指定、発火時に読み上げる `message` 必須。同時4件まで |
| `get_weather` | v9.20 の天気取得を再利用（`day_offset` 0=今日／1=明日／2=明後日／7=週間要約） |
| `get_train_delays` | v9.21 の運行情報取得を再利用（田園都市線・大井町線・南武線） |
| `get_news` | 既存ニュース取得を再利用（48時間鮮度フィルタ・既読スキップ込み、見出し＋説明を返す） |
| `get_current_datetime` | JST の現在日時・曜日 |
| `remember_fact` | 長期記憶への即時保存（下記と共通の保存処理） |

- タイマーは Scheduler 基盤へ単発タスク（`ScheduleTimerOnce`）として登録します。発火判定は loop 側でも行うため、**相対タイマーは NTP 未同期でも発火**します（Scheduler の `run_schedule()` は時刻未同期時に早期 return するため）。絶対指定は現在時刻が同期済みのときだけ受け付け、過ぎた時刻は翌日に回します。発火時は既存の発話キューに載せ、発話中なら終わるまで待ち（上限10分、超えたら破棄してログ）、中央タップで中断もできます。再起動するとタイマーは消えます。
- フォールバック：tools 付きリクエストが API エラー（400等）を返したら tools なしで1回だけ再試行し、通常会話として成立させます（モデルは /model の選択どおり変えません）。引数 JSON が壊れていたらエラーをモデルへ1回だけ返し、2回目で会話を壊さず「うまくできませんでした」と発話します。ログは `[FC]` 接頭辞（関数名と成否のみ、引数の個人情報は出しません）。
- 既存のキーワード分岐（天気・電車・ニュース）は速い経路として従来どおりチャットの前に処理され、変更していません。複合リクエスト（「明日の天気と電車の遅れを教えて」）や言い換えは AI 経由のツールで処理されます。
- 天気・運行情報は、読み上げ文の生成部を `buildWeatherText()` / `buildTrainText()` に分離してツールと共用しました（発話へのセットは従来のラッパーが担当し、挙動は不変）。

**長期記憶メモリ**:

- 保存先は **microSD の `/memory_facts.txt` 優先、なければ SPIFFS**（/digest/ と同じ選択方式で、初回アクセス時に決まります）。1行＝1件の短い事実文（UTF-8）、上限 **40件・約4KB**、超過時は古い順に削除します。
- 会話への反映：`init_chat_doc` の直後に、保存済みの事実一覧を「ユーザーについて覚えていること」としてシステムプロンプトへ追加します（0件なら追加しません）。
- 自動抽出：音声会話の応答を話し終わった後、loop のアイドル時間（発話・合成・BLE がなく Wi-Fi 接続済みのとき）に1回だけ抽出 API を呼びます。入力は直近のやり取り＋現在の事実一覧、出力は更新後の事実一覧の JSON 配列だけを厳密に返させ、検証（配列・文字列のみ・件数・総バイト数）を通った場合のみファイルへ書き戻します。失敗は `[MEM]` ログのみで会話に影響しません。抽出は会話に使っているモデル（/model の選択）を使い、HTTPS は CheckedTlsClient / TlsGate の規律に従います。
- 明示保存：「覚えて：〜」に応える `remember_fact` ツールで即時保存し、保存した旨が返答に含まれます。
- 管理ページ：本体 Web の `GET /memory`（一覧＋追加フォーム＋件ごとの削除）、テスト用 `GET /memory_json`。本体ホームからもリンクしています。外部公開はしません（従来ページと同条件）。
- **書き込み（フルフラッシュ）で SPIFFS は初期化されますが、SD 側の `/memory_facts.txt` は消えません。** 記憶を残したい場合は SD カードを入れて使ってください（保存先は /memory ページで確認できます）。

Core2ビルド成功・既存回帰27件成功。ファーム 3,604,880 bytes、SHA-256 `3ff3b456f046c814b63c4353c70890ec22792ff5cacc4a06040bfa44d0895cc5`。**実機での動作は未確認**です（ツール呼び出しの実応答、タイマー発火、抽出の成否、ヒープ推移は本体で要確認）。配布（書き込みページ）は本版 v9.25 に更新しました。

Muse／ChatGPT／Codex が検索・要約したテキスト（ITニュース、GitHub ランキング、Hugging Face ランキング等）を BLE で本体へ転送して保存し、ニュースとして読み上げる機能を追加しました。BLE スタックは NimBLE（h2zero/NimBLE-Arduino 1.4.3、ペリフェラル専用にセントラル／オブザーバ・ロールを無効化）を使います。

受信はオンデマンド方式です。BLE は常時 ON にせず、`GET /ble` で受信モードを開始したときだけ ON になります（書き込みページの「テキスト転送」欄からも開始できます）。受信待ちは3分間で、画面には吹き出しで「BLE受信待ち」と出ます。転送完了（保存後15秒）またはタイムアウトで自動的に OFF に戻ります（`NimBLEDevice::deinit` でスタックごと解放）。開始・終了時は `[BLE]` ログにヒープ残量を出します。音声の再生・合成・発話待ちがある間は受信モードを開始しません（`/ble` は 409 を返します）。受信モード中は定期読み上げ・朝のスケジューラ・中央タップ会話を開始せず、転送と競合しないようにしています。

GATT 設計（128bit カスタム UUID）：サービス `e8f5a001-b7d3-4c1e-9a2b-3d4c5e6f7081`、CTRL `e8f5a002-…`（Write：`BEGIN:<総バイト数>`／`END`／`ABORT`）、DATA `e8f5a003-…`（Write、1書き込み最大180バイト、応答あり）、STATUS `e8f5a004-…`（Read／Notify：`WAIT`／`RECV n/m`／`DONE <ファイル名>`／`ERR …`）。デバイス名は `StackChan-Digest`、MTU は 185 を要求します。受信データは PSRAM 上の一時バッファに組み立て、`END` 時に総バイト数を検証してから正式保存します。途中切断時は部分データを破棄して受信待ちに戻ります。

保存先は microSD の `/digest/` を優先し、カードが使えない場合は SPIFFS にフォールバックします（キャプチャと同じ優先順位）。形式はプレーンテキスト UTF-8（1行目＝タイトル、以降＝本文）で、ファイル名は `dg_NNNN.txt`、保持は最新10件（古い順に削除）、1件の上限は 60KB です。

読み上げへの組み込み：ニュースのカテゴリに「転送ニュース」（6番目、LED 色は紫）を追加し、選ぶと最新の保存テキストを読み上げます。本文は改行位置で文を区切り、既存の文分割パイプライン（speech_text＋2行字幕＋中央タップ中断可）で読み上げます。定期読み上げと朝のスケジューラ読み上げでは、未読の転送テキストがあれば最新の1件をニュースの後に続けて読み上げ、既読にします（繰り返し読まない）。既読は最新の読み終えた連番を NVS（setting/dgread）に保持し、ニュースの既読記録と同様に書き込みでリセットされます。テスト用に `GET /digest`（最新の転送テキストを読み上げ開始）も追加しました。書き込みページの「テキスト転送」欄では、タイトル＋本文を入力し、「BLEで送信」ボタンで Web Bluetooth 接続して CTRL→DATA（180バイト刻み）→END の順に送り、STATUS で保存結果を確認します。

IRAM 対策について：BT コントローラ（prebuilt の libbtdm_app.a）が約28KB の IRAM を占有し、そのままでは iram0_0_seg（128KB）が超過してリンクできませんでした。コントローラ側は変更できないため、追加リンカスクリプト `move_time_to_flash.ld` で、タスク文脈からしか呼ばれない libc の時刻系オブジェクト（strftime／strptime／mktime／gmtime 系／tzset 系、合計約9KB）だけを IRAM からフラッシュへ移しています（ISR やフラッシュ書込みのクリティカル区間からは呼ばれない純粋な文字列・時刻計算処理です）。あわせて platformio.ini に NimBLE のロール無効化フラグを追加しています。

## 手順

### 1. ビルド

必要なもの：VSCode＋PlatformIO（または PlatformIO Core の CLI）

```bash
cd M5Unified_AI_StackChan
pio run -e m5stack-core2
```

成果物は `.pio/build/m5stack-core2/firmware.bin` です。
環境：espressif32@6.3.2、M5Unified 0.1.16（詳細は `platformio.ini`）。

### 2. 本体への書き込み

**方法A（推奨・ブラウザで書き込み）**
書き込みページ一式が private リポジトリ `2ndarystorage/stackchan-core2` の `ai_stackchan_flasher/` フォルダにあります。

1. そのリポジトリを ZIP でダウンロードして解凍する
2. 解凍したフォルダ内の `ai_stackchan_flasher` で `python3 -m http.server 8000 --bind 127.0.0.1` を実行する
3. Chrome で `http://localhost:8000` を開く
4. Core2 を USB で接続し、ページの案内に従ってシリアルポートを選んで書き込む

書き込み内容：bootloader（0x1000）／パーティション（0x8000）／NVS初期化（0x9000）／boot_app0（0xe000）／アプリ本体（0x10000）／SPIFFS初期化（0xc90000）。
※ NVS と SPIFFS が初期化されるため、書き込み後は WiFi・APIキー・ウェイクワードの再設定が必要です。

**方法B（esptool で直接）**
上記のオフセットに各バイナリ（bootloader.bin / partitions.bin / boot_app0.bin / firmware.bin）を書き込んでください。

**元に戻したい場合**
公式コミュニティ版 stack-chan v2.0.1 は公式 Web インストーラ（https://stack-chan.github.io/stack-chan/web/flash/）から書き直せます。

### 3. 初期設定（WiFi / APIキー）

microSD カードのルートに2つのファイルを作って入れる方法が確実です。

- `wifi.txt`：1行目に SSID、2行目にパスワード
- `apikey.txt`：1行目に OpenAI キー、2行目に VOICEVOX キー（tts.quest）、3行目に STT キー（Whisper を使う場合は OpenAI キーと同じもの）

カードを入れて電源を入れ直すと接続され、画面に IP アドレスが表示されます。
WiFi 未設定のまま起動すると「Waiting for SmartConfig」を表示して再起動を繰り返します（故障ではありません）。

### 4. 使い方

- **ウェイクワードの登録**（最初の1回だけ）：本体の **Bボタン（下段まん中）を2秒長押し** →「ウェイクワード登録開始」と表示されたら、呼び名にしたい言葉（例：「こむぎ」）を1回はっきり言う → 登録した声が再生され「登録終了」と出れば完了。ウェイクワードは文字ではなく自分の声で登録する方式です
- **会話の始め方**：**Aボタン（下段左）** を押して「ウェイクワード有効」にしてから登録した言葉で呼ぶ。または画面の「STT」表示あたりをタッチしても会話が始まります
- **ニュース**：「ニュース教えて」のように「ニュース」を含めて話しかけると、最新ニュースを読み上げます
- **電池残量**：Cボタン（下段右）で読み上げます
- **独り言モード**：放っておくと時々独り言を言います。Bボタン長押し（ウェイクワード登録）をすると止まります

### 5. ブラウザ設定ページ一覧

本体と同じ WiFi から `http://stack-chan.local`（開けない場合は本体表示の IP アドレス）で開けます。

| ページ | 内容 |
|---|---|
| `/voice` | 声（話者14種）の切り替え・試聴、話速（1.0〜1.3倍）の切り替え |
| `/model` | AIモデルの切り替え |
| `/news` | ニュース読み上げをその場で実行 |
| `/speech?say=文章` | 任意の文章を喋らせる（`&voice=話者ID` で一時的に声変更可） |
| `/face?expression=0〜5` | 表情変更（0:Neutral 1:Happy 2:Sleepy 3:Doubt 4:Sad 5:Angry） |
| `/setting?volume=&led=&speaker=` | 音量・LED・話者IDの直接設定 |
| `/apikey` `/role` | APIキー設定／ロール（キャラ設定）編集 |

### 顔と表情について

- 顔は M5Stack-Avatar ライブラリが描画しています（画像ファイルではありません）。カスタム版の顔は `src/PenguinFace.h` です
- 表情ごとにエフェクトが出ます：Happy=ハート（右上）、Angry=怒りマーク、Doubt=汗、Sad=チルマーク、Sleepy=鼻ちょうちん
- ハートは主に「発話中」「会話開始時（『御用でしょうか？』）」に表示されます
- サーボを使う場合の GPIO は `main.cpp` で設定（現在のビルドは Core2 PORT A：X=GPIO33 / Y=GPIO32）。サーボ未接続でも動作します

## Program Summary
* M5Stack-based “AI Stack-chan” that records audio, runs speech-to-text (Google Cloud STT or OpenAI Whisper), sends chat to OpenAI, and speaks responses via VOICEVOX TTS.
* Includes on-device avatar/face animation, optional servo movement, wake-word handling, and a small HTTP server for settings (API keys, role, speech/face controls).
* Stores configuration in NVS/SPIFFS and can load Wi-Fi/API keys from SD card files.
* This fork adds: a penguin face, web pages for voice/speech-rate/model selection, faster responses (silence-based recording stop, max_tokens cap), and NHK news headline reading triggered by the word 「ニュース」.

## Completion Status
Stock code verified on real hardware (M5Stack Core2) on 2026-10-27. Custom v1 (penguin face, /voice, /model, speedups) also verified on device the same day. Custom v2 (speech-rate control, news reading) is built but **not yet verified on the device**.
