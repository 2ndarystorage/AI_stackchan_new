# ニュース音切れ対策 v9.12

対象: 2026-11-01に報告されたv9.11のログ。更新対象はAI_stackchan_newのソースとstackchan-core2の配布ファーム。

## ログとコードから分かったこと

- 約1.24秒想定の最初の音声が約8.9秒かかっています。MP3供給を行う `mp3->loop()` はメインloopに1回だけ置かれ、同じloopのJPEG準備・LCDロック待ち・UI処理に影響されます。音声用PCMは1バッファ320フレーム（24kHzなら約13ms）と小さく、メインループで長時間待つ構成は音切れを起こせます。実機での寄与の大きさは修正版ログで確認します。
- スピーカー出力が `playRaw` の失敗を確認せずバッファを進めていました。またstopで未再生PCMを停止・ゼロクリアしていました。これらは音声欠落につながる実装上の問題です。
- `consumed=0` / `early-stop` は終了処理後の値でした。AudioGeneratorMP3のstopがソースをcloseし、AudioFileSourcePROGMEMの位置は0へ戻るため、読み出し量を正しく計測できていませんでした。MP3末尾で出るERROR_BUFLENだけではファイル破損・デコード能力不足は断定できません。
- 先頭30バイトの短い文を単独で合成し、次の合成＋取得に約7.5秒かかるのにプリバッファが5秒で切れています。先頭音声の約1.24秒では次の準備が間に合わず、文間に空白が生まれます。
- `isApiKeyValid: NG` とHTTP429が出ています。TTSサービス側がキーを有効と認めておらず、少なくとも当該リクエストが制限されています。無効キーが429の唯一の原因とは断定できません。ソフトウェア変更だけでサービスの待ち時間をなくすことはできません。
- I2Sの登録失敗1回はMic→Speakerの切替直前です。既存M5Unifiedの再登録経路と一致し、これだけで再生失敗とは判定しません。

## 変更

1. MP3供給をcore1・優先度2の専用タスクに分離。begin・decode・stopは同一mutexで直列化し、中断時に使用中データを解放しないようにしました。完了通知はatomicでメインloopへ渡します。
2. PCMキュー投入が拒否されたときはデータを保持して再試行。自然終了時には最大1秒だけキューの排出を待ち、中断時には即停止します。
3. メモリソースはclose後も最終読み出し位置を保持。終了時間はメインloopが気付いた時刻ではなくデコーダータスクの完了時刻を使い、`max_decode_gap`（デコーダー呼出間隔の最大ms）も記録します。
4. 短い先頭案内も後続文と約300バイトまでまとめ、合成回数を減らします。最初の2チャンクを待つ上限を20秒に延ばしました。初回の待ち時間は増えますが、短い案内だけ先に流れて止まるケースを減らします。句読点判定の「、」と全角「！」「？」の取り違えも修正。
5. PSRAMのMP3作業領域は維持。v9.10で問題になった約38KBの内蔵ヒープ常駐には戻していません。追加のデコードタスクは8KBスタックを使用します。
6. 無効なVOICEVOXキーを受信した場合、`/apikey` の確認を案内します。Retry-Afterの扱いとTLS証明書検証は維持しています。

## 検証

`c++ -std=c++11 -I tests/native tests/native/audio_regression.cpp -o /tmp/stackchan-audio-regression && /tmp/stackchan-audio-regression`

スピーカー拒否時の再試行、1200サンプルの欠落なし・順序維持、文末排出待ち、close後・二重close後の位置保持を模擬スピーカー／依存ソースで確認。旧出力ヘッダーに差し替えた試験では文末排出のassertが失敗し、修正後は成功しました。実機のI2S・TLS・音声品質はこのテストの対象外です。

## 書き込み後の確認

- 起動ログに `[BOOT] MP3 decoder task ready (core=1 priority=2 v9.12)` が出ること。
- 本体の `/apikey` に有効なVOICEVOX APIキーを設定し、次の合成で `isApiKeyValid: OK` になるか確認。キーをログやGitへ貼らないでください。
- ニュース1件と連続ニュースで、音声の途中の途切れと文間の待ちを分けて確認。
- 終了ログのconsumedが総バイト数近くに達すること、elapsedとexpect_wallが大きく乖離しないことを確認。consumedはデコーダーが先読みしたバイト数であり、スピーカー再生完了の保証ではありません。
- 429が残ればサービスの制限と契約を確認。プリバッファを増やしても、音声生成の平均速度が再生より遅い回線・サービスでは文間待ちは残ります。
- ニュース中断、次の会話、音量変更、ダンス後のニュースを確認。

本作業では実機への書き込み・API課金を伴う試験は行いません。音切れ解消の最終判定には同じ本体での再生試験が必要です。
