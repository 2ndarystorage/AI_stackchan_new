# v9.16 左上バージョン表示・I2S切り替え修正・TLS診断

更新: 2026-11-01。**X509エラーの根本原因・実機での解消は未確認**です。この版は判明したI2S切り替えとログ分類を修正し、証明書失敗の安全な停止・原因切り分けを追加します。

## 今回のログから分かること

- v9.15で2文の合成・取得が成功。327,949/327,949 bytes・161,389/161,389 bytesまで読み出し、実時間13,639/6,716msも想定13,659/6,719msに近く、両方`reason=natural`、`failed_chunks=0`です。前回のダウンロード失敗とTLS二重確保とは異なります。ログだけで実際の聞こえ方までは保証しません。
- `MP3:ERROR_BUFLEN 0`は、この2件では入力終端に達した時のログです。数字はデコーダの連続回数で、すべてのBUFLENを正常扱いしてはいけません。
- `isApiKeyValid: NG`はキー未受理、HTTP 429はサービス側のレート制限です。合成200の応答でもNGになっており、証明書エラーとは別問題です。キーの有効性・無料枠制限は`/apikey`とサービス側で確認が必要です。
- 次のNHKニュースはRSS取得200後、`api.tts.quest`でX509 -9984が継続。空きヒープ約85KB・最大連続ブロック約43KBで、今回のログにSSL -32512のメモリ不足はありません。X509の詳細flagsが旧版では解放時に消えるため、期限・時刻・信頼CA・ホスト名等のどれが原因かは現状断定できません。

## 修正

### 左上にv9.16を表示

版は`src/FirmwareVersion.h`を共通定義とし、左上(2,2)の52×16px黒帯に白文字で表示します。Avatarの顔・吹き出し合成完了後、同じグラフィックスロック内で描くため上書きされません。ダンスとニュース一覧にも同じ描画を行います。追加描画タスクは作らず、フォント・文字スタイルを復元します。起動ログは`[BOOT] Firmware v9.16`です。

### I2Sドライバを解放してからマイクへ

固定依存M5Unified 0.1.16の`Speaker_Class::end()`はタスク停止後もI2Sドライバを残します。次の`Mic.begin()`が登録失敗→アンインストール→再登録へ進み、今回のエラーログにつながります。スピーカーが動いていた場合だけ、タスク停止を待って所有ポートを解放してからマイクを開始する共通関数に置換しました。マイクが所有するドライバは誤って解放しません。会話中のウェイクワード登録開始も抑止し、サーボ切替の確認音を既存の安全な切り替え経路へ統一しました。

### MP3終端の表示を区別

入力全量を読み出した場合の**最初の**`MP3:ERROR_BUFLEN 0`だけを`[MP3] buffer refill at source EOF (decoder continues)`へ分類し直します。入力途中・連続回数1以上・他のエラーはそのまま出力します。デコーダ・MP3データ・停止判定は変更せず、全エラーを黙らせる処理ではありません。

### 証明書を無視せず、詳細を保持して安全に停止

Arduino 2.0.9のTLS接続処理でエラーが返った直後、`stop()`が状態を消す前に詳細を記録するクライアントを追加しました。既存のTLS開始関数を使い、元のCA・SNIホスト名・必須検証を保ったまま、失敗時のIP・検証flags・取得できた場合の発行者と有効期間を記録します。`setInsecure()`、検証flagsのクリア、HTTPへのダウングレードはしていません。APIキーやURL全文を追加ログに出しません。CA自体はv9.15のX1/YRのままで、根拠なく再差し替えしていません。

証明書失敗は同じ文の再試行と残りの未合成キューを停止し、画面にもエラーを表示します。取得済みで正常な文は再生可能です。次のニュース開始は手動で再試行できます。429の待機・一時通信エラーの再試行は維持しています。

```text
[TLS] verify_failed host=api.tts.quest ip=... error=-9984 flags=0x........
[TLS] peer_issuer=... valid=....-..-.....-..-..
[TTS] session halted: certificate verification failed; inspect [TLS] flags
```

flagsは複数の理由を含められます。主な値は`0x01`期限切れ、`0x04`ホスト名不一致、`0x08`信頼CAへの署名検証失敗、`0x0200`有効期間前。`0xFFFFFFFF`は詳細を取得できない状態として扱い、信頼成功とはしません。エラー直前の`[TLS] synth ... epoch=...`も合わせて確認します。

## 検証

- Core2ビルド成功（`pio run -d M5Unified_AI_StackChan -e m5stack-core2`）。依存ライブラリの既存deprecated警告等は残ります。
- `python3 -m unittest discover -s tests -v`: **14件成功**。I2S切り替え100往復・既存マイクを解放しないこと、版表示の位置・文字・描画順・スタイル復元、EOFログ限定分類と長い行の保持、実TLSクライアントのヘッダーをモックでコンパイルして解放前のflags取得・検証維持を試験。既存の描画競合・音声キュー・キャンセル・証明書等も維持し、証明書失敗時の残キュー停止を追加検証。
- C++音声回帰試験成功（`tests/native/audio_regression.cpp`）。
- 補助試験としてPCで公式Mbed TLS 2.28.1をビルドし、製品のCAバンドルだけでapi/audio1/audio2.tts.questおよびnews.google.comのTLS 1.2ハンドシェイク成功。誤ったCAだけを指定する負の試験は-9984／flags=0x08で拒否されました。**HTTP要求・APIキー送信は行っていません**。補助環境構築の初回は新しいCMakeの互換設定・Clangの警告エラーで失敗しましたが、互換オプションと補助ビルドの警告設定変更で成功しました。製品ビルドのセキュリティ設定は変更していません。
- 検証用Cソースは`tests/native/tls_handshake.c`。公式Mbed TLSのincludeとlibmbedtls/libmbedx509/libmbedcryptoにリンクし、`HOST CA_PEM`を引数に実行します。補助PC試験はESP32向けパッチ・ハードウェア暗号・実機のネットワーク環境を再現するものではなく、今回の断続的X509失敗は再現できていません。
- 配布生成はv9.16起動版・MP3/TTS・TLS詳細ログ・EOF分類とv9.13ロックのマーカー、CA指紋を検証。全パーツのサイズ・SHA-256・アドレス・ビルドとのバイト一致を確認。旧v9.15入力は想定どおり拒否し、配布を変更しませんでした。
- 配布4モジュールの構文検査成功。
